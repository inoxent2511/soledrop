# In-app authentication migration

This records M4 implementation and its test scope. Runtime MySQL selection and request-scoped authorization are M5/M8 work; production browser acceptance remains M10. Existing storefront/admin screens and copy are unchanged.

The first-party fallback preserves two separate identity tables, cookie names and opaque sessions stored only as SHA-256 hashes. Better Auth's current [session schema](https://better-auth.com/docs/concepts/session-management), [2FA defaults](https://better-auth.com/docs/plugins/2fa) and [Drizzle adapter](https://better-auth.com/docs/adapters/drizzle) were checked. Its documented recoverable session token and default passwordless assurance behavior need a custom lifecycle to meet this brief. This is a fit decision, not a claim that the library generally lacks those features.

Passwords use Node scrypt N=32768, r=8, p=3, random 16-byte salts and 64-byte derived keys, with NFKC normalization. This is the [OWASP 32 MiB profile](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html). Imported N=16384 hashes remain valid and upgrade after a successful login without revoking other sessions. A parameter upgrade uses a compare-and-set credential write. Verification performs equivalent work for older profiles; startup warms the random dummy hash before accepting traffic. HTTP auth wrappers apply a common response-time floor with small jitter. Actual production timing distributions are part of M5/M10 acceptance, not inferred from unit results.

The existing password form constraints remain. A small offline common-password deny-list rejects known weak choices when setting a new password. It sends no password/digest to a third party and is explicitly **limited coverage**, not a full compromised-password corpus. No HIBP request or real email is made during local migration QA.

TOTP uses maintained otplib 13.6.0 with explicit SHA-1, six digits, 30-second steps and one-step drift. Existing sealed secrets retain their format/key derivation; preserve the stable authentication secret during configuration migration. Accepted steps and recovery-code removals use optimistic compare-and-set updates. Concurrent proof consumption, enrolment, session upgrade, reset and invite acceptance run in database units of work with consistent store-first locks. Mandatory audit failures roll those protected mutations back. Failed-login counters commit before returning a generic credential error. AAL2 requires an enrolled factor and a non-null proof timestamp at the repository boundary, with an additional database assurance CHECK.

Staff sessions retain 30-minute idle and 12-hour absolute limits; password-only pending sessions last 15 minutes. AAL2 receives a fresh token. Password changes revoke old sessions and issue a replacement while retaining the actual earlier MFA timestamp; proving a password does not refresh the second factor. Sensitive existing operations retain the ten-minute step-up window. Customer/staff cookies are HttpOnly, Secure in production and SameSite=Lax; every cookie-authenticated mutation and public auth mutation requires an exact trusted Origin. Plain HTTP loopback is allowed only with the existing explicit insecure-cookie preview setting. Bearer-only jobs/webhooks can omit Origin.

New delivery events seal bearer-link payloads with purpose-separated AES-256-GCM before queue storage. Only the email renderer opens them. Plain and sealed bearer fields are excluded from third-party event payloads. The private frozen legacy snapshot remains unchanged; normalization of previously queued legacy payloads is a retirement/import concern and must preserve delivery capability.

Optional backend capabilities are disabled by default, so no new UI controls are introduced:

| Configuration / endpoint | Behavior |
| --- | --- |
| AUTH_MAGIC_LINK=on; POST /api/auth/magic-link | Uniform success for known/unknown email; 15-minute hashed single-use token; binds sign-in to an HttpOnly initiating-browser cookie |
| AUTH_EMAIL_VERIFICATION=on; POST /api/auth/verify-email | Uniform response; 15-minute hashed single-use email proof |
| GET /api/auth/link | Validates capability and, for magic sign-in, browser binding; verification alone never creates a login; redirects to the existing account screen with no-referrer |
| OIDC_ISSUER / OIDC_CLIENT_ID / OIDC_CLIENT_SECRET | All-or-none HTTPS OIDC configuration. POST /api/auth/oauth/start and GET /api/auth/oauth/callback use openid-client 6.8.9 |
| OIDC protocol | S256 PKCE, state, nonce, initiating-browser binding, signature/JWKS, issuer, audience, expiry and verified-email checks. Five-minute single-use state, sealed verifier, no stored provider access/refresh tokens. Provider subjects include a store-scoped provider key. Existing local accounts require a password-confirmed linking request; email alone never auto-links identities |
| GET /api/auth/sessions; DELETE /api/auth/sessions | Authenticated customer lists/revokes only their sessions; identifiers are non-recoverable token hashes |
| PATCH /api/auth/email | Current-password proof and credential compare-and-set, old-address security notice, session rotation and verification reset |
| ADMIN_IP_ALLOWLIST | Optional comma-separated IPv4/IPv6 address/CIDR restriction, validated at startup and checked using trusted proxy metadata for login and every staff DAL request; denied requests audited |

Owner bootstrap: `pnpm admin:create-owner --email owner@example.com` runs locally or over SSH against a loopback database using configured credentials. Under a store lock it refuses an existing active Owner, installs the permission registry, revokes older unused bootstrap invites and writes one hashed invite valid for 24 hours. It prints only the one-time set-password link, never creates/stores a plaintext password, and still requires authenticator enrolment. Tests use only fresh task-owned test stores. The preserved merchant Owner is not recreated or modified.

The shared service contract runs on fixtures and both real engines, including rollback after credential/audit failures, parallel reset/invite/enrolment/recovery consumption, realm separation, lockout, credential rotation, stale reauthentication, verification, session ownership and OAuth identity/state persistence. OIDC protocol tests intercept every provider request with locally generated signed tokens and JWKS; they never contact a provider. Existing fixed-clock fixture tests inject that same clock into the fixture repository so expiry checks retain their original meaning.

Still required by later stages: current-session/grant validation at every raw repository call, generated route/ownership matrices, production cookie/timing assertions, the full browser regression/parity loop, real authenticator/device checks and owner-verified host/SMTP facts. Read-only customer preview is an optional M7 capability; it must never mint a customer mutation session.
