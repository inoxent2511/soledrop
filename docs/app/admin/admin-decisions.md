# Admin — decisions

Migration update: runtime storage is MySQL/MariaDB with explicit actor/store guards, live transactional staff authorization and table grants instead of PostgreSQL RLS/triggers. Existing decision IDs below retain their original rationale. Current operational controls and limits are in [security.md](./security.md) and [the deployment runbook](../../DEPLOYMENT-RUNBOOK.md).

Same format as [../design-decisions.md](../design-decisions.md). Kind: **security**, **derived** (no design or brief covers it), **scope** (in or out, with the reason).

| ID | Kind | Where | Decision | Why |
| --- | --- | --- | --- | --- |
| A-001 | security | Staff identity | Staff sign in with the app's own staff auth: scrypt password hashes (the customer `password.ts`), hashed opaque session tokens in an `httpOnly` cookie (`sd_staff`, path `/`, `SameSite=Strict`), and mandatory TOTP (RFC 6238, SHA-1, 30 s, 6 digits) implemented with `node:crypto`. Staff and customer sessions are separate tables and cookies; a customer session never authenticates a staff member. | The brief suggests the former identity provider MFA, but this environment has no the former identity provider to run against (no Docker / the former platform CLI), and the storefront already uses in-house sessions. One model on both data drivers (`fixtures`, `the former platform`) makes the whole admin runnable and testable offline. Moving staff identity to the former identity provider later only changes `server/admin/auth`; **needs owner decision**. |
| A-002 | security | MFA | MFA is mandatory: a password-only session is AAL1 and can only reach the enrolment and verification screens; every other admin route requires AAL2. First sign-in shows the enrolment (secret as QR + text, confirm with a code) and ten single-use recovery codes, stored hashed. | Brief: mandatory TOTP, AAL2 for `/admin`, recovery codes. |
| A-003 | security | Step-up | Sensitive actions need a fresh second factor (TOTP within the last 10 minutes on this session), asked by `StepUpDialog`: refunds above the role's step-up threshold, role and permission changes, staff invite/suspend/MFA reset, customer export and anonymise, API-key creation, payment/webhook settings, bulk deletes. | Brief 2.1. |
| A-004 | security | Sessions | Idle timeout 30 min, absolute 12 h; "sign out everywhere"; active sessions list (device, IP, last seen) with per-session revoke; suspending a staff member or changing their roles revokes all their sessions immediately. | Brief 2.1. |
| A-005 | security | Brute force | Login is rate-limited per address (10 / 5 min) and per email (5 / 15 min, then a 15-minute lockout); TOTP verification 5 / 5 min per session; one generic error message for any failure, and a decoy hash is checked for unknown emails so timing doesn't reveal accounts. | Brief 2.1 (no enumeration, lockout). |
| A-006 | security | Three layers | (1) `proxy.ts` redirects `/admin/**` without a staff cookie to `/admin/login`; (2) `requireStaff()` / `requirePermission()` (`server/admin/dal.ts`, `server-only`) open every admin page, route handler and server function; a test fails the build if an admin route or handler has no declared permission; (3) every new table has RLS enabled with no policy for `anon` and policies through `has_permission(store, permission)` (`SECURITY DEFINER`, `search_path = ''`) for the former platform-Auth staff. The server reaches the database with the service role only after layer 2 passed. | Brief 2.2. Layer 3 is written for the former platform-Auth identities (see A-001); with in-house staff sessions it guarantees that the anon key and customer tokens can read or write nothing admin-side. |
| A-007 | derived | Roles data | Permissions live in one typed registry (`server/admin/permissions.ts`), seeded to `permissions`; preset roles are seeded with `is_system = true` (cannot be deleted; Owner cannot be edited). The legacy `staff_members.role` enum column is kept for the existing phase 1 policies but no longer required (`drop not null`); RBAC uses `staff_roles`. | Additive migrations only. |
| A-008 | security | Last Owner | A trigger rejects any change that would leave a store with no active staff member holding the Owner role (suspend, role removal, deletion). The service checks first to give a readable message. | Brief: at least one active Owner, enforced in the database. |
| A-009 | scope | Reviews & Q&A | Not built: the storefront has no reviews or questions, so there is nothing to moderate. | Building reviews is a storefront feature first (data model, product page UI, moderation); listed for phase 3. |
| A-010 | scope | Blog, banners | Not built: the storefront has no blog and no banner slots. | Nothing would consume them. |
| A-011 | security | Demo staff | `ADMIN_DEMO_STAFF=on` seeds one **DEMO** staff member per preset role into the fixtures driver (`<role>@demo.soledrop.local`, password `Demo-Staff-2026!`, TOTP secret derived from the role key, `server/fixtures/admin-seed.ts`) so the admin can be run and the e2e suite can sign in without a database. Off by default; environment validation refuses it with `DATA_DRIVER=the former platform`, so demo accounts can never exist in a real database. | The fixtures store lives in the server's memory, so no script can add an Owner to it; the brief asks for clearly marked, removable demo accounts. |
| A-012 | security | Admin CSP | `/admin/**` is served with a per-request nonce CSP from `proxy.ts` (`lib/admin-csp.ts`): `script-src 'self' 'nonce-…' 'strict-dynamic'`, no `'unsafe-inline'` for scripts; every admin page renders per request (the admin layout calls `connection()`) so Next stamps the nonce on its scripts. The root layout's theme provider is skipped on `/admin` (the admin is light-only), because its inline script can't carry a nonce on statically rendered storefront pages and its hash changes with every build's minification. Styles keep `'unsafe-inline'` (Base UI positions popups with style attributes). The storefront keeps its static CSP (D-033). | Brief: nonce CSP for the admin. Admin pages are per-request anyway (they read the session), so the nonce costs no caching. |
| A-013 | derived | Owner bootstrap | The first Owner comes from `pnpm admin:create-owner --email you@…` (`scripts/create-owner.mjs`), which writes a one-time Owner invite into the **local** the former platform database (it refuses any non-local `the former platform_URL`) and prints the `/admin/invite/<token>` link; the person sets a password and enrols MFA there. On a production database the owner runs the same SQL insert through their own console (runbook). | No email provider sends invites yet; the brief forbids touching remote databases from here. |
| A-014 | security | Media uploads | Images are accepted by their bytes (JPEG/PNG/WebP/AVIF magic numbers), at most 10 MB and 40 megapixels, then decoded and re-encoded with sharp to WebP (≤ 2400 px, metadata dropped); anything sharp can't decode is refused. Files are served from `/media/<uuid>.webp` with `nosniff`, `Content-Security-Policy: default-src 'none'; sandbox` and a year's immutable cache. Storage: the former platform Storage bucket `media` (created by the owner, runbook) with the `media` table as index; the fixtures driver keeps files in process memory. SVG is not accepted (it can carry script). | Brief: secure uploads. Re-encoding is what makes a polyglot or EXIF/GPS leak impossible, not the extension check. |
| A-015 | derived | Prices in the product form | Price fields need `pricing:write` (Store Manager and up); a Catalogue Editor builds drafts without prices and someone with pricing access prices them. Publishing needs a photo and a base price for every size. A refused price change saves nothing (checked before the write). | The preset matrix gives Catalogue Editors `pricing:read` only; publishing an unpriced size would put an unbuyable pair live. |
| A-016 | derived | Storefront freshness | Every catalogue save, import, stock change and collection change calls `revalidatePath("/", "layout")`, so ISR pages (home, product pages) show the change on the next request instead of after their 60–300 s window. With the fixtures driver in `next dev`, editing a seed file still resets catalogue tables to the seed (D-060 refresh). | A small catalogue makes a full refresh cheap; per-path tags can come later. |
| A-017 | scope | Policy pages | Terms, Privacy, Shipping & Delivery and Returns are designed documents in code (`content/*.ts`, D-054…D-057) built from the owner's PDFs; the admin links to them but doesn't edit them, and their slugs are reserved for block pages. Block pages (`/pages/<slug>`, drafts until published) and the FAQs are edited in the admin. FAQ edits go live at once, so they need `content:publish`. | Legal wording is versioned with the site (reviewable diffs) and the documents have bespoke layouts the block model doesn't cover. |
| A-018 | security | Integrations | API keys, webhook endpoints, payment and email credentials stay in the server environment (`API_KEYS`, `WEBHOOK_ENDPOINTS`, `STRIPE_*`, `RESEND_API_KEY`, `BANK_*`); the admin shows what is configured (key names and scopes, webhook hosts, provider status), never a secret, and doesn't create keys. Feature flags are switched in the admin; an environment override (`FEATURE_FLAGS`) wins and the switch says so. | Secrets in the database would be one more place to leak them, and rotating them is a deployment task. Creating keys in the admin is phase 3 (needs a hashed key table and a one-time reveal). |
| A-019 | derived | Notifications | The notification centre is computed on request from live data (orders to pack, bank transfers waiting, sold-out sizes, failed emails/webhooks), filtered by the member's permissions, and refreshed every minute; nothing is stored or emailed. | No new table to keep in sync; the counts are always true. |
| A-020 | security | Browser validation and CSP | Browser schemas import the `lib/validation.ts` setup before Zod; it sets `jitless: true` before schema construction. Server-only validation can still import Zod directly. An architecture test guards import order, and auth e2e checks actual CSP violation events as well as console errors. | Firefox reports even Zod's caught dynamic-code capability probe under the strict admin CSP. Validation must avoid the probe; the CSP is kept strict. The setup has no namespace re-export, to preserve tree shaking. |
| A-021 | derived | Saved local store | Normal local work defaults to a saved single-process file driver, reusing the domain repository operations behind a serialized queue. Snapshots are checksummed and atomically replaced; private media lives beside them. Fixtures are an explicit isolated QA mode, and the former platform remains the hosted path. | Preview edits/uploads previously disappeared on restart. No hosted database is configured here; the owner authorized retaining the live catalogue. A one-time import preserves existing records without reseeding on boot. |
| A-022 | scope | Banners and merchandising | The Content sidebar includes Banners & images. Homepage hero/category/Instagram content is saved per store; collection editors own page banner images, including dedicated New Arrivals, Sale and Pre-Loved routes. Publishing requires the existing content/collection permissions. Media deletion checks all product statuses, collections, homepage and purchased image snapshots. | The owner requested admin controls for every banner currently displayed by the site and removal of static merchandising data. |
