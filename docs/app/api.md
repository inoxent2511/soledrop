# HTTP API

Four surfaces, one error shape. The machine-readable contract for the headless API is
`GET /api/v1/openapi.json` (generated by `server/http/openapi.ts`).

## Errors (every endpoint)

```json
{ "error": { "code": "out_of_stock", "message": "Only 1 left in EU 44.", "details": {} } }
```

| code | HTTP | | code | HTTP |
| --- | --- | --- | --- | --- |
| `validation` | 422 (`details.fields` per field) | | `rate_limited` | 429 + `Retry-After` |
| `promotion_invalid` | 422 | | `invalid_transition` | 409 |
| `out_of_stock` / `conflict` | 409 | | `payment_failed` | 402 |
| `unauthorized` / `forbidden` | 401 / 403 | | `unavailable` | 503 |
| `not_found` | 404 | | `internal` | 500 (no detail leaked; logged with a digest) |

Messages are written for shoppers. Actor-aware repositories raise domain errors;
`server/db/client.ts` normalizes engine errors without exposing SQL or bound values.

## 1. Storefront API (`/api/*`): cookies, same origin

Used by the storefront's React Query hooks (`hooks/api/*`). They are authenticated by the httpOnly
cookies `sd_cart` and `sd_session` (SameSite=Lax, Secure in production), with an Origin check on
every mutation and `Cache-Control: private, no-store`. Prices and totals are always computed on the
server; clients send only ids, quantities and codes.

Per-address limits key on the `X-Forwarded-For` entry appended by our own outermost proxy
(`TRUSTED_PROXY_HOPS`, default 1). Entries to its left are client-written and ignored (BUG-015).
Sign-in is also limited per email address.

| Method · path | Purpose | Rate limit |
| --- | --- | --- |
| `GET /api/cart` · `POST /api/cart` `{variantId, quantity}` | Read / add to the bag | add: cart 120/min |
| `PATCH · DELETE /api/cart/lines/{lineId}` | Change quantity / remove | cart |
| `POST /api/cart/codes` `{code}` · `DELETE /api/cart/codes/{code}` | Apply / remove a promotion | apply: lookup 20/5 min (code guessing) |
| `POST /api/checkout/quote` | Totals for an address + delivery choice (read-only) | — |
| `POST /api/checkout` + `Idempotency-Key` (16–80 `[A-Za-z0-9_-]`) | Place the order (atomic; a repeat key replays the first order) | checkout 10/min |
| `GET /api/orders/{number}?token=` · `POST …/cancel` · `POST …/returns` | Guest/customer order access by signed token or session | — |
| `POST /api/orders/lookup` `{number, email}` | Find an order (one message for any mismatch) | lookup 20/5 min |
| `POST /api/auth/{register,login,logout,forgot-password,reset-password}` | Accounts | auth 10/5 min per address (login also per email) |
| `GET · PATCH · DELETE /api/account`, `GET /api/account/export`, `POST /api/account/password`, `/api/account/addresses[/{id}]` | Profile, data export, erasure, addresses | — |
| `GET /api/search/suggest?q=` | Search overlay data, one trimmed DTO `{ query, total, suggestions, collections, brands, products, didYouMean, trending, popular }`. ## 2. Headless API (`/api/v1/*`): API keys

`Authorization: Bearer <key>` (or `X-API-Key`). Clients are configured in `API_KEYS`
(`name:key:read+write`). Keys are compared as SHA-256 digests in constant time, and each client is
limited to 600 requests/min. Responses carry `x-api-version: 1`. Every write is attributed to
a distinct SHA-256-derived API-client identity in the audit log and order history.

| Method · path | Scope | Body / query |
| --- | --- | --- |
| `GET /api/v1/products` | read | storefront listing filters + `collection`, `kind=new\|preloved`, `pageSize ≤ 100`, `customerGroup` |
| `GET /api/v1/products/{slug}` | read | — |
| `GET /api/v1/collections` | read | — |
| `GET /api/v1/products/export` | read | CSV, one row per variant |
| `POST /api/v1/products/import[?dryRun=1]` | write | `text/csv` ≤ 5 MB; all-or-nothing; 422 with a per-row report |
| `GET /api/v1/orders/{number}` | read | — |
| `POST /api/v1/orders/{number}/transition` | write | `{to, note?, trackingNumber?}`, validated by the state machine |
| `POST /api/v1/orders/{number}/payments` | write | `{provider: cod\|bank_transfer, amount, reference?, idempotencyKey}` |
| `POST /api/v1/orders/{number}/refunds` | write | `{amount, reason, lines[], restock, idempotencyKey}`; never exceeds what was paid |
| `POST /api/v1/returns/{id}/receive` | write | Restocks the returned pairs |

Amounts are integers in the minor unit (paisa): `1499900` = Rs. 14,999.

## 4. Admin API (`/api/admin/*`): staff session, same origin

For the admin UI only (no stable contract for third parties: use `/api/v1` for integrations). Every
handler is `adminRoute(access, …)` (`server/admin/route.ts`): the staff cookie `sd_staff`
(`SameSite=Strict`), our own `Origin` on every mutation, `Cache-Control: private, no-store`, and at most
120 writes a minute per session. `access` is a permission (403 without it), a permission with step-up
(403 with `details.stepUp: true` until `POST /api/admin/auth/step-up` proves a code), `staff` (any AAL2
member), `pending` (finishing MFA) or `public` (sign-in, invites). The permission each endpoint needs is
declared in its file and checked again inside the service. `e2e/admin-permissions.spec.ts` checks
every preset role against its listed 24 read APIs and 17 module pages; integration suites cover
selected write permissions. Coverage limits are in [admin/verification.md](./admin/verification.md).

Public file route: `GET /media/{id}.webp` (media library images; `nosniff`, sandboxed, cached a year).
The shared loader requests one of six prepared widths (320/640/960/1280/1920/2400); the route
negotiates WebP/AVIF and supports ETag/304 without encoding images during requests. Private
attachments require a fresh, authorized capability with a maximum five-minute lifetime.

Refund requests use durable intents and stable provider keys. Uncertain provider outcomes remain
reserved for reconciliation; a retry cannot create an independent refund for the same intent.
Use the loopback reconciliation command in [admin migration](admin-migration.md) for investigation.
